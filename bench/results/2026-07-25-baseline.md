## Notes on failure patterns

**Fixed this session**: the `fun`/`fn` mismatch (2 tasks) — resolved by
adding `fun` as a lexer synonym for `fn` (cheap, no breaking change).
Also: `01`/`11`'s missing-import failures now surface as `did you forget
to import the standard library List?` instead of the confusing `unknown
constructor 'List'` (`typechecker.ml`'s `Constr` inference case checks the
unresolved name against a hardcoded stdlib-module list). This doesn't make
either task's code correct — both still legitimately fail, since the
`import` is still missing — but it turns a misleading error into an
actionable one, and the README's REPL-vs-script import distinction was
also tightened (it was already stale: it claimed `Process` preloads in the
REPL when it doesn't, and omitted `Map`/`Regex`, which do).

**Remaining, not yet actioned**:
- Task 01/11's `import`-omission pattern suggests the README's REPL-vs-script
  distinction for "which stdlib modules are in scope without importing" is
  easy to misread. Worth a clearer callout if this recurs in future runs.
- Task 09's `let rec` silently misparsing (rather than erroring clearly on
  the unrecognized `rec` token) is a language/error-message quality issue
  independent of this benchmark's original purpose.
- Task 08 is the one failure that's specifically a *generics* gap (not a
  general syntax-fluency issue) — it should flip to a pass once
  `.claude/plans/generics.md` lands, and is the primary thing to re-check
  in the next run.

Parse-rate: 8/12 (67%). Excluding the generics-specific failure (08), the
non-generics parse/pass rate is 8/11 (73%) — the delta this benchmark is
meant to isolate is specifically task 08 flipping after generics ships.
