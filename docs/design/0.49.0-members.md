# 0.49.0: a bundle for `Args`, and members a file can write

Notes from the discussion that followed 0.48.1. Nothing here is built. The
facts were checked against the binary; the sketches were not.

## Already on main for 0.49.0

One commit: a value cannot take the name of a type or a constructor.
`type Pod(host: String)` beside `let Pod = 1` used to be accepted, and the
value could not be reached from anywhere. Held back from 0.48.1 because it
rejects code that used to compile.

## What derivation is

The compiler keeps the declaration. When a file writes `T.member`, the value
is computed from that declaration then. Nothing is stored, and nothing is
generated ahead of time.

Five members exist: `decoder`, `encoder` (0.41.0 and earlier), and `usage`,
`spec`, `reader` (0.47.0). The names are hardcoded in `lib/typechecker.ml`
and `lib/evaluator.ml`.

Add a field to a declaration and all five change with it. That is the whole
value: there is no second copy to drift.

Three limits, all reached in this discussion:

- The set is five. A file cannot add a sixth.
- A file cannot replace one.
- Derivation that reaches another type reads that type's *declaration*, never
  a value a file wrote. `Outer.decoder` cannot use a custom `Inner` decoder.

## The bundle

`Args.read` takes two derived members that are only ever passed together, and
nothing stops one type's `spec` meeting another type's `reader`.

    type Parser 'a(spec: Map String, reader: Decoder 'a, usage: String)

    Args.read Opts.parser (Env.args ())

`Parser` is declared in `stdlib/Args.wand`. `T.parser` is a sixth derived
member. `Args.read` changes signature, which breaks anything written against
0.47.0 or 0.48.x.

A user can write the bundle today in five lines, and it runs:

    type Parser 'a(spec: Map String, reader: Decoder 'a, usage: String)
    let read : Parser 'a -> List String -> Result String 'a =
      fn p argv -> Args.read p.spec p.reader argv
    let opts = Parser(spec = Opts.spec, reader = Opts.reader, usage = Opts.usage)

This only became possible in 0.48.1. Both fixes in that release were on this
path: a field could not hold a `Decoder`, and a written signature did not
bind `p` before `p.spec` was read.

### Naming, undecided

`parser` says what it is for. `command_line` says what it is about. `cli` and
`arg_parser` were rejected: an initialism where no other member has one, and
a stutter against the module.

If `spec` and `reader` are retired, `parser` is the only public name for the
job. `usage` should stay public whatever happens, because
`Opts.parser.usage` is a step deeper for every `--help` line.

## Members a file can write

    let Opts.usage = "probe [options] <host>"
    let Inner.decoder = my_decoder

This is not sugar for `let opts_usage = ...`. Nothing looks a member up
unless a file writes it, so where the name lives changes nothing on its own.

The one case it changes is derivation that calls derivation. `Outer.decoder`
picks its field's decoder by itself, so there is no call site to pass a
custom one at. Today the only fix is to hand-write the outer decoder, and
everything containing it.

Three rules make the sketch work. Each is a decision:

1. Derivation reads members, not declarations. `Opts.parser` asks for
   `Opts.spec` and gets the written one if there is one. This is what makes
   replacement compose, and it is the whole point.
2. A member is declared in the file that declares the type. Then there is one
   definition and no choice to make. Allowed elsewhere, `Outer.decoder`
   depends on which files were loaded.
3. A written member replaces a derived one silently, or says so:
   `let override Inner.decoder = ...`. Undecided.

## What this does not need, and what it does not give

Static members and derivation are both resolved by a file writing the name.
Neither is dispatch.

    Args.read Opts.spec Opts.reader argv   -- today
    Args.read Opts.parser argv             -- the bundle
    Args.read Opts argv                    -- needs types as values
    Args.read argv                         -- needs resolution from the
                                              expected type: a trait system

The same wall stands in front of `List.sort` on a type you define. A member
puts the comparison somewhere findable. It does not let `sort` find it from
inside a function that does not know the type. `List.sort_by` is the answer
that works, and is why `docs/gaps.md` still records ordering as a gap.

`class`, `instance` and `orphan` have been reserved words since the first
lexer commit. Nothing uses them.

## Facts worth keeping

- A `Decoder` reads JSON. `TOML.decode` converts TOML to JSON and runs the
  same decoder. `CSV` has no decoder. A custom format is supported by parsing
  it into `JSON` and calling `JSON.decode`.
- Equality is structural on any type. Ordering is not: a type you define
  cannot be compared with `<`.
- `T.reader` and `T.decoder` have the same type, `Decoder T`. They differ in
  which document they expect. For a type that is all flags they are the same.
- A typo on a member says `constructor 'F' has named fields; construct it as
  F(port = ...)`. It never mentions members. `wand v` does not accept a type.
  Discoverability of the five is close to zero, and is worth fixing whatever
  else is decided.
